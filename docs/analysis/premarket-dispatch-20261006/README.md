# Premarket: discovery, бюджет и координатор

Дата: 6 октября 2026. Область: только offline-реализация и синтетические тесты.
Статус: `OFFLINE_INTEGRATION_VERIFIED_PILOT_NOT_READY`.

## Выполнено

В `trading_mvp/src/premarket_depth_dispatch.py` реализован и проверен маршрут:

`четыре каталога Gate/OKX -> нормализованные события -> выбор пакета -> резерв бюджета -> существующий последовательный координатор`.

Чтение каталогов передаётся через явный transport-адаптер. В этом запуске вместо
бирж использованы только искусственные ответы. Старый `scan()` со скрытым
`_spawn_capture` не вызывается. Из замороженного watcher используются только
чистые парсеры каталогов и существующее правило отбора.

Каждый scan держит один global writer claim. Перед capture этот claim освобождается,
а существующий координатор атомарно занимает его снова. Это два последовательных
этапа, не два одновременных writer. Если между ними claim займёт другой процесс,
capture не начнётся. Бюджет capture резервируется после получения claim.

## Общий бюджет

SQLite-журнал хранит настройки, историю изменений с цепочкой хэшей, уникальные
идентификаторы запросов, исходные нормализованные отчёты и неизменяемые пакеты.
Транзакции `BEGIN IMMEDIATE` и `synchronous=FULL` защищают от параллельного
списания и обычного прерывания процесса. Существующий журнал нельзя обнулить
повторной инициализацией. Это контроль технической целостности, не защита от
злоумышленника, который может переписать всю базу и пересчитать хэши.

Перед запросом сохраняются одна попытка и верхний предел ответа. После точной
квитанции освобождаются только неиспользованные байты. Если процесс оборвался,
резерв остаётся списанным, а следующий запрос блокируется. Повтор одной попытки
и повторное освобождение её резерва запрещены. Выделенный output-бюджет неполного
пакета тоже не возвращается автоматически.

| Лимит | Реализованное ограничение |
|---|---:|
| Поиск расписания | не чаще одного scan в 900 секунд |
| Длительность одного scan | 300 секунд |
| Metadata-запросы одного scan | 4, без скрытого collector |
| Scans за кампанию | не более 4 032 |
| Metadata HTTP / body | 16 128 попыток / 18 GiB |
| Book HTTP / body | 38 400 попыток / 6 GiB |
| Общие HTTP / body | 54 528 попыток / 24 GiB |
| Captures / пакеты | максимум 24 / 24 |
| Общий output | 2 GiB |
| Резерв журнала / отчёта scan | 256 MiB / 16 KiB |
| Резерв capture-пакета | 64 MiB |
| Первый пилот до проверки качества | ровно один пакет, максимум два события |

Лимиты являются независимыми потолками, не обещанием израсходовать их все.
Размер журнала также ограничен SQLite `max_page_count`. Временный rollback journal
SQLite и служебный сетевой трафик не выдаются за полезный body/output; необходим
дополнительный свободный диск, как требует существующий координатор.

Через 14 дней от будущего включения действует обязательная остановка для проверки;
42 дня остаются абсолютной внешней границей. Автоматическое прохождение проверки
на 14-й день не реализовано. После первого пилота журнал переходит в
`PILOT_REVIEW_REQUIRED`, а при незавершённом сборе в `STOPPED_INCOMPLETE`.
Само наличие лимита 24 capture не разрешает ещё 23 запуска без технического разбора
первого пакета. Это не запрос повторной фразы пользователя.

## Отбор и привязка

- Сохраняются исходные Gate/OKX, USDT, порядок perp-before-spot, lead, окна и
  минимум 12 независимых пригодных событий. Доходность не читается.
- Equity reference отдельного Listing Momentum не вызывается. Отсутствие проверки
  типа актива помечено явно; событие по этому признаку не исключается.
- Пакет привязан полным `batch_hash` к `plan_hash`, runtime hash, точному
  `source_report_hash` и списку событий. Изменённый отчёт с прежним количеством
  событий нельзя подставить вместо сохранённого.
- Учитывается вся группа перекрывающихся окон, включая ещё не начавшиеся окна.
  Больше двух событий означает `CAPACITY_BLOCKED`, а не выбор удобных монет.
- Если вся группа не помещается в четыре часа, выдаётся `WINDOW_SPAN_BLOCKED`.
  Это ограничение ресурсов и возможная потеря покрытия, не новый торговый фильтр.
- Старый scan, пропущенное начало и невозможность закончить до проверки на 14-й
  день блокируют пакет до создания capture output.
- Повтор уже обработанной пары venue/base не запускается. Перенос её времени
  после capture отдельно даёт `SCHEDULE_CHANGED_ALREADY_CAPTURED`; второй сбор
  по новой метке времени автоматически не выполняется.
- Сырые каталоги не сохраняются. Из квитанции ответа берутся только разрешённые
  поля размера/хэша; дополнительные payload-поля не попадают в отчёт.

## Проверки и реальные действия

30 новых тестов, включая цепочку scan-to-coordinator, прошли. Вместе с прежними
тестами координатора, общего claim, sampling, качества и checkpoint: **136/136**.
Выполнение было в отдельном видимом PowerShell, PID/команда сохранены в
`visible-launch.json`, полный вывод в `visible-verification.log`.

Проверены конкурентные резервирования, повторное открытие журнала после
незавершённого запроса, хэши и подмена отчёта, общий и отдельный HTTP-бюджет,
байты, output, календарные границы, занятый чужой writer, ошибки источника,
пропущенные/перекрывающиеся события и отсутствие повторного capture.

Все рабочие журналы, claims и captures тестов находились во временных папках.
Биржевых запросов не было. Production writer claim и capture namespace отсутствуют.
Два premarket-расписания и `Trading MVP Weekly Forward Collect` остались Disabled.
Старые данные, базовый план, coordinator v1, его launcher и controller не изменены.

Полный suite проекта не запускался. Ранее известный сбой старого теста Listing
Momentum из предыдущего этапа здесь не исправлялся и повторно не проверялся.

## Готовность пилота

**Пилот пока не готов к реальному запуску.** Это не остановка на approval token.
Причины технические и явно отражены в `verification.json`:

1. Новый слой пока предоставляет offline-проверенное ядро с явными transport и
   guard callbacks. Отдельный сетевой gateway, вызываемый видимым launcher и
   связывающий эти callbacks с проверенной публичной сетью и свежим controller,
   ещё не установлен. Прямой запуск старого координатора обойдёт бюджет кампании
   и не может быть использован вместо такого gateway.
2. Рабочая кампания, её время начала/остановки, журнал и будущий пакет не выбраны
   и не созданы. Текущие тестовые события не являются реальными кандидатами.
3. Действующий controller по-прежнему разрешает только offline-этап. Расписания
   остаются выключенными. Его нельзя подменить успешным synthetic-тестом.

Следующий технический этап: подключить ядро к видимому gateway без обхода budget
ledger, проверить его на искусственном transport, затем выполнить технический
rebind. В этом отчёте готовность сетевого пилота не заявляется.
