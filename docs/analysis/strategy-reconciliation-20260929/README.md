## Исправление контроллера

Новая готовность родительского проекта привязана к этому аудиту и текущему v6-плану, а не к изменяемому состоянию вынесенного Listing Momentum. Старый v24-report и preimage policy/pointer/gate сохранены. Любое изменение входных данных, их списка, плана или связанного runtime снова закрывает checkpoint до технического согласования.

Все три команды используют одну готовность: `check_trading_mvp_autopilot.ps1`, `trading_goal_status.ps1`, `trading_next_goal_step.ps1`. Квота, RUNNING, STOPPED_INCOMPLETE, неизвестный gate и наличие writer claim продолжают блокировать запуск. `READY_FOR_POSTPROCESS` старого basis-run не трактуется как право читать отклонённый dataset; replay/backtest остаются запрещены в этой контрольной точке.

Закрытые гипотезы, старые Dense/PIT окна и branch-disposition не переоткрываются. Сведения о выключенных Windows tasks и PAUSED Codex automations сохранены отдельно. Ни одно расписание не включено.

## Следующий эксперимент

**Рекомендация, не активированное расписание:** оставить один действующий вопрос из `premarket_forward_depth_20260902_v6`: уходит ли bid-depth перед/вместе с падением после открытия spot. Не добавлять новый сигнал, новый рынок, подбор порога или новую ветку.

1. До дальнейшего анализа явно определить технический учёт пропусков, неполных top-25 и одновременных листингов. Использовать только информацию о качестве и времени, не доходности. Если это меняет содержательный контракт анализа, зафиксировать новую версию до расчётов, а не выбирать правило по результату.
2. Сохранить порог **не менее 12 событий**, причём три текущих кандидата являются только верхней оценкой уже пригодного материала. Старые v3-v5 не использовать для искусственного достижения порога.
3. После решения о возобновлении ранее отключённого расписания предложить bounded-сбор по тому же scope: контроль качества через 14 календарных дней, общий горизонт не более 42 дней. Общую величину HTTP/дискового бюджета и runtime следующего запуска определить и заморозить до включения; это не разрешение на бесконтрольную работу 42 дня.
4. Обоснование горизонта: в старом плане указана приблизительная частота одно событие в четыре дня. Даже при зачёте всех трёх нужно ещё девять, то есть около 36 дней при такой частоте. Эта частота относится к прежнему описанию нескольких площадок, не измерена для текущего пригодного набора Gate/OKX и не гарантирует срок. 42 дня являются предложенным пределом расходования времени, а не обещанием набора выборки.
5. Если за 14 дней новых технически пригодных событий нет, пересмотреть достижимость, не расширяя scope автоматически. Если к 42-му дню порог не достигнут, завершить попытку как `INFEASIBLE_FOR_CURRENT_RESEARCH_HORIZON`, не снижать порог и не продолжать бесконечный сбор.
6. Только после достаточной и проверенной выборки выполнить один frozen descriptive-анализ. Он способен отвергнуть механизм, но не принять торговую стратегию. Для стратегии затем нужен отдельный заранее заданный торговый контракт, независимые данные и экономические/OOS-ворота.

Ближайшая неделя используется для проверяемой готовности эксперимента, а не для обещания прибыльной стратегии. Ни отсутствие выборки, ни описательный механизм не являются положительным торговым результатом.
