# Совет: расширение бирж/монет и организация прогонов (2026-07-15)

Метод: 5 независимых агентов-ролей (first-principles, contrarian, upside, operator, domain-quant) с общей доказательной базой; сырые вердикты сохранены в workflow-журнале `wf_427cf5a6-9f8`. Research-only, не инвестсовет. Синтез: Claude Code.

## Решение (нейтрально)

Q1: какой охват universe (биржи × монеты) использовать для следующих треков?
Q2: как организовать прогоны (частота/длительность/параллельность), чтобы вердикты достигались за дни-недели, а не месяцы, и прогоны не шли сутками?

## Опции и позиции ролей

**Q1**: 4/5 ролей — (d) поэтапная комбинация: Binance-listed на MEXC/Gate (≈0 инженерии, прецедент 02.07) → Bitget (нужен cost-профиль) → Bybit/OKX только access-проба. Контрарианец — (a) ядро non-Binance, Bitget только для того же тезиса, Binance-listed только как стратифицированная контрольная группа.

**Q2**: 4/5 — (c)+(d): PIT-трек не трогать; ночное окно расширить до 2–4ч; параллельный быстрый бэкфилл-трек на 4h-барах (вердикты за 1–3 недели). Контрарианец — (d)+(a): бэкфилл только как измерительный инструмент; плюс легальное ускорение PIT.

## Разногласия, которые имеют значение

1. **Бэкфилл: трек гипотез или только измерение?** Trade-off: скорость вердиктов vs survivorship-заражение последнего трек-слота. Разрешается фактами (все роли сошлись на одних тестах): survivorship-аудит по архивам делистингов (порог ~10–15% недостижимых имя-дней), event-census на замороженном наборе, effective-N block-bootstrap. Снимается двухфазным протоколом: фаза A — сбор+census как ОПИСАТЕЛЬНОЕ измерение (не тратит multiplicity), фаза B — открытие трек-слота отдельным решением пользователя по фактам.
2. **Binance-listed: пулить или стратифицировать?** Consensus после сверки: НИКОГДА не пулить с non-Binance для добора порога ≥20 событий (химера популяций); только стратифицированный dual-run с раздельными вердиктами.
3. **1h или 4h?** Квант-математика решает: 4h — основной таймфрейм бэкфилла (издержки 10–30% σ), 1h — только для моделирования исполнения.

## Единогласные пункты (все 5 ролей)

- PIT-forward сегмент 23:00–23:20 неприкосновенен: данные невосполнимы, каждая ночь без записи потеряна навсегда.
- Ворота не ослабляются ни в одном сценарии; бэкфилл-ACCEPT ≠ продуктовый ACCEPT (максимум SCREEN_PASS, лестница probe→paper→live обязательна).
- Bybit/OKX не строить до end-to-end пробы доступа.
- Новые датасеты чеканят новые слоты гипотез → считать датасеты дорогими, а не бесплатными (анти-отмывание multiplicity).

## Находка контрарианца, принятая всеми (легальное ускорение PIT)

План фиксирует 100 OOS-дней, но ворота требуют лишь OOS ≥60 дней И ≥20 событий. **Пре-регистрированное правило остановки OOS-сбора «max(60 дней; до 20 событий; cap 100)», слепое к PnL**, экономит до ~40 календарных дней без касания единого инварианта. Плюс расширение ночного PIT-захвата (universe + Bitget) повышает плотность событий будущего OOS-окна → вердикт PIT-трека ~2.5–3 мес вместо 4.

## Рекомендация

**Вердикт: proceed with guardrails (поэтапно, с kill-тестами до траты бюджетов).**

Почему: корень проблемы — дефицит событий при незанятых дешёвых рычагах (96% ночного окна свободно, REST-история не используется, Bitget-проба лежит принятой). Скорость достигается конверсией календаря в REST-историю и шириной, а чистота — неприкосновенностью PIT-трека и двухфазным протоколом. Ничто не ослабляет ворота.

### План первой недели (сетка operator, ~18–21ч инженерии, ночи ≤3.5ч из 8)

1. **Сегодня**: батч из четырёх запросов пользователю (см. ниже); access-пробы Bybit/OKX (2×30 мин); конфиг Binance-listed dual-run (~2ч).
2. **День 1–2, блокирующий**: survivorship-аудит (архивы делистингов MEXC/Gate за 12–18 мес, klines 30–50 делистнутых символов) → одно число в decisions.md; kill-порог >10–15%.
3. **День 2–3**: cost-профиль Bitget в costs.py; заморозка хартии бэкфилл-трека ДО сбора (4h основной, 1h только execution; universe-правило = trailing 30d ADV-ранк PIT из самого бэкфилла; SCREEN_PASS-семантика).
4. **Ночи 3–5**: REST-бэкфилл 4h (+daily) 12–18 мес × top-200 × 3 биржи (~1–2ч/биржа, диск <2 ГБ) после неприкосновенного PIT-сегмента; Merkle-freeze.
5. **День 6**: описательный event-census (минуты; multiplicity не тратится) + effective-N; go/no-go меморандум пользователю по открытию 3-го трек-слота.
6. Кандидат №1 для заморозки на новом датасете — семейство v4 (18/20 событий на малом наборе; новый Merkle = легально).

### Запросы пользователю (батч, всё обратимо)

а) активация Bitget (проба принята 09.07); б) расширение ночного сегмента с 20 мин до 2–4ч в рамках одобренного окна (PIT 23:00–23:20 не трогается); в) подтверждение записи Binance-listed universe (прецедент 02.07; запись ≠ торговля); г) пре-регистрированное правило остановки OOS «max(60; до 20 событий; cap 100)».

### Stop conditions

- Survivorship-аудит >10–15% недостижимых имя-дней → бэкфилл понижается до measurement-only, Q2 схлопывается в (d)+PIT.
- Event-census <20 событий/venue даже на 4h/12–18 мес → рычаг частоты/истории мёртв; фокус на ширину PIT-захвата.
- Round-trip издержки >25–40 bps на целевых именах → Bitget/интрадей исключаются из reversion-трека.
- ACCEPT на v6 или PIT-треке → вся экспансия замораживается, 3ч/день уходят на paper-forward победителя.
- Сбои утверждённого PIT-сегмента 2 ночи из 7 из-за расширенных ночных работ → откат к 20-минутному расписанию.

### Residual unknowns

Доступ Bybit/OKX (проба, 30 мин); реальная доля survivorship (аудит, 2ч); event-rate PIT-трека (feasibility-мемо по накопленным ночам); глубина истории klines/funding Bitget.

## Ответ на вопрос «как часто запускать прогоны»

Прогоны НЕ должны идти сутками, и при этой схеме не идут: **дневные** — только оценки/QC/census (секунды–минуты, лимит 3ч не приближается); **ночные** — сборы ≤3.5ч из 8 с hard-deadline 07:00 (PIT 20 мин + бэкфилл/расширенный захват); **еженедельные** — funding forward (авто, уже работает). Долгие календарные ожидания остаются только там, где они физически неустранимы (PIT-forward), и сокращаются правилом остановки с 4 до ~2.5–3 месяцев — параллельно быстрый трек даёт вердикты каждые 1–3 недели.
