## Простое объяснение

Ночной сбор данных можно оставить без изменений. Проблема находится после него: программа должна сначала проверить качество файлов, а потом построить причинные метки режима. Сейчас оба шага делят один общий лимит в 30 минут.

Измерение на 300 000 реальных строках старого диагностического набора показало нижнюю оценку около 43 минут для ожидаемых 25 018 151 строк. Поэтому единый лимит 30 минут, скорее всего, закончится раньше обработки.

## Что проверено

- Обработка потоковая: весь файл не загружается в память.
- Максимум 16 пар на площадку; состояние обрезается до скользящего окна.
- Пиковая отслеживаемая память синтетической нагрузки: 4.405 MiB.
- Проверка качества: прогноз 1234.884 секунды.
- Хеширование, чтение и причинная обработка: прогноз 1325.103 секунды.
- Общая нижняя оценка: 2559.987 секунды, или 42.666 минуты.
- Текущий лимит: 1800 секунд; нехватка не менее 759.987 секунды.
- Целевые тесты: 18/18 PASS.
- Fast regression: 262/262 PASS.

## Безопасное решение

Оставить утвержденный collector и PlanOnly без изменений. Для postrun применить два отдельных видимых лимита:

1. Проверка качества: максимум 1800 секунд.
2. Причинная materialization: максимум 1800 секунд.

Итого общий предел 3600 секунд. Evaluator, returns, PnL, OOS, grid, retune, paper/live и private API этим не разрешаются.

Изменение общего runtime-контракта требует отдельного точного разрешения пользователя. До него остановлена только postrun-ветка; ночной сбор остается утвержденным.
